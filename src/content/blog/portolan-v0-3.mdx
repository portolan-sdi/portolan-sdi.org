Portolan v0.3.0 came out on 2026-11-17. When we started on it, most of the
open questions came from the same place: people who wanted to publish data
that did not quite fit the specification yet. Tables written by lakehouse
engines. Raster archives that a browser could not show at a glance. Data
cubes in Zarr. Catalogs so large that finding a collection meant reading
hundreds of JSON files. This release is our answer to those questions. Some
of the answers are firm, and some are first drafts that we want you to try.

The post marks each change as one of two kinds. **Normative**
changes are part of conformance. Validators check them, and a conformant
catalog follows them. **Incubating** specs are written down, with their own
requirement IDs, but they are not part of conformance yet. They can change
before we make them normative, and your feedback decides how. The [full
changelog](https://github.com/portolan-sdi/portolan-spec/releases/tag/v0.3.0)
lists every change.

## Parquet that geospatial tools did not write (normative)

Until v0.3, Portolan vector data had to be GeoParquet. Meanwhile, Parquet
added its own support for geometry. The format now has native `GEOMETRY` and
`GEOGRAPHY` types, and more engines write them, including Apache Iceberg
writers. A table written that way is clearly vector data, but earlier
validators treated it as a plain table, because it had no GeoParquet `geo`
metadata.

v0.3 accepts GeoParquet 1.1, GeoParquet 2.0, and Parquet with native geometry
types, and it applies the same vector rules to all three. We recommend
GeoParquet 2.0 when your tools can write it. It stores geometry in Parquet's
own geometry type, so any Parquet reader recognizes it, and the file includes
bounding box statistics for each row group. It also keeps the `geo` metadata,
which records the CRS in the file.

For a data team, this means files that come out of the lakehouse they
already use can go straight into a catalog.

## Rasters you can see and read (normative)

With a collection of hundreds of raster tiles, a browser either draws one
tile or tries to draw all of them. v0.3 says that a collection of
many rasters should include an overview COG: one small image in a web map
projection that shows the whole collection at once.

Classified rasters, such as land cover, now describe their classes with the
[STAC](https://stacspec.org/en/) classification extension. A client can then
draw a legend that says "forest" and "water" and not "class 3" and "class 7".
Imagery should also declare its nodata value, so clients stop drawing the
empty edges of a scene as black.

## Metadata that explains itself (normative)

Portolan has always asked for documentation next to the data. v0.3 goes one
level deeper. Table columns should have descriptions, and assets should have
a title and a description. A column called `dtvw` means nothing until the
catalog tells you it is the average weekday traffic count. People need that
sentence, and so do agents.

## Data in the bucket where it lives (normative)

Many catalogs keep their data in S3 or Google Cloud Storage. v0.3 lets assets
link with `s3://` and similar schemes, as long as they also give an https
alternate for clients that only speak HTTP. Servers that are S3-compatible but
not on AWS are described with the STAC storage extension, so clients know
where to send the request. Range requests are now required only for the data
files that need them (COG, Parquet, PMTiles, and COPC), so a host that serves
only the metadata can be a plain static server.

This is also where v0.3 breaks things. Partition globs must now be absolute
bucket URLs, such as `s3://` or `gs://`. A reader has to list the files that
match a glob, and you cannot list files over plain HTTP or with a relative
path. In October 2026, this affected 9 of 37 collections in the registry. To fix
it, replace the relative glob with the bucket URL. A related rule requires each
data asset to link to one file. Another says that PMTiles cannot be a
collection's only data. PMTiles is the visual layer, and it must point to the
GeoParquet it was made from.

## Spatial order, measured differently

Rows in a GeoParquet file must still follow a spatial order. That rule is still
**normative**. We changed how we check it. The old test looked at how
much the row groups overlapped, and it failed files that were well sorted but
had only a few row groups. We removed it.

In its place, an **incubating** method measures what spatial order is for:
the share of a file that a typical query can skip. Validators report it as a
warning only, while we calibrate it on real catalogs.

## STAC-GeoParquet as a catalog (incubating)

v0.3 defines how a Portolan catalog publishes itself as
[STAC-GeoParquet](https://github.com/portolan-sdi/portolan-spec/blob/v0.3.0/specs/incubating/stac-geoparquet.md).
One GeoParquet file has a row for every catalog and collection in the tree, with its
extent, time range, keywords, links, and full original JSON. The catalog
becomes a table that any Parquet reader can open. The JSON stays the normative
form. The layout follows the shape proposed upstream in the [stac-geoparquet
spec](https://github.com/radiantearth/stac-geoparquet-spec/issues/17), which is
still under discussion and not released. The schema can still change a bit,
and Portolan will follow upstream when it does.
Many catalogs in the registry already publish one, and the registry will
publish one for all of them. I will write a separate post about STAC-GeoParquet as a
catalog.

## Zarr (incubating)

Portolan started with [GeoParquet](https://geoparquet.org/),
[PMTiles](https://docs.protomaps.com/pmtiles/), and [COG](https://cogeo.org/).
But a lot of climate, weather, and Earth observation data is published as
[Zarr](https://geozarr.org/), and we do not want those publishers to convert
their data cubes to fit us. v0.3 adds an [incubating Zarr
profile](https://github.com/portolan-sdi/portolan-spec/blob/v0.3.0/specs/incubating/zarr.md)
for Zarr v3 raster stores. If you publish data cubes, this is the part of the
release where we most need your feedback.

## Apache Iceberg (incubating)

Iceberg is new in v0.3. The [incubating
convention](https://github.com/portolan-sdi/portolan-spec/blob/v0.3.0/specs/incubating/iceberg.md)
lets a catalog publish an [Apache Iceberg](https://iceberg.apache.org/) table
over the GeoParquet it already serves. STAC is still the catalog, and it
describes the data. The Iceberg table is a second
way in, for the engines that speak Iceberg.

Both paths end at the same bytes. The live data files of the table are exactly
the collection's data assets, so the table adds metadata, not a second copy of
the data. A reader also needs no server. The collection points to the table's
metadata file, and an engine opens the table from that file alone.

A static catalog gains a lot from this. The table's manifests list every file,
so a client can read a partitioned collection over plain HTTPS without listing
the bucket. Per-file bounds let an engine skip a file without opening it. The
convention uses
Iceberg format version 3, the first with a native geometry type, over
GeoParquet 2.0 data files. It works in both directions: a publisher can
register existing GeoParquet as a table, or point the catalog at files an
Iceberg engine wrote first.

## Validate with rashid 0.4

A spec release is only useful if a validator checks it. [rashid
0.4.0](https://github.com/portolan-sdi/rashid/releases/tag/v0.4.0) came out
on the same day, 2026-11-17, and it implements the v0.3 rules. It bundles the
v0.3.0 profile schema and checks the new rules, such as native geospatial
Parquet, column descriptions, raster classes, and absolute partition globs. It
also checks the incubating parts: it checks a Zarr store against the
incubating profile and reports spatial order as a warning.

rashid applies the newest rules it knows, whatever version your catalog
declares, and it reports both versions. So it shows you what v0.3 would flag
before you move.

```bash
uv tool install rashid
rashid check path/to/catalog
```

## Try it

Read the [specification](https://spec.portolan-sdi.org/), and declare v0.3 in
your catalog with
`https://schemas.portolan-sdi.org/portolan/v0.3.0/schema.json` in
`stac_extensions`. The earlier schemas are still published, so nothing changes for
a catalog until you move it. Then run rashid, and tell us what works and what
does not in the [Portolan Google Group](https://groups.google.com/g/portolan)
or the [Portolan
channel](https://cloudnativegeo.slack.com/archives/C0A1JBH9529) in
Cloud-Native Geo Slack.
