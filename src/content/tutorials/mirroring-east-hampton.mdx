In this tutorial, we'll cover a simple example of publishing East Hampton, New York's open data as a Portolan catalog. By the end, you'll know how to use the Portolan `bootstrap`agent skill to orchestrate an end-to-end conversion of an existing Esri server to a complete Portolan catalog, published on Source Cooperative. (Note: the example here is an unofficial mirror of East Hampton's data, not an officially-endorsed catalog.) In future tutorials, we'll dive deeper on some of what's going on under the hood, including topics like [generating nice thumbnails](https://github.com/portolan-sdi/portolan-skills/blob/main/skills/portolan-thumbnails/SKILL.md), [git-backed Portolan catalogs](https://github.com/portolan-sdi/portolan-skills/blob/main/skills/git-backed-catalog/SKILL.md), and [publishing to Source Cooperative](https://github.com/portolan-sdi/portolan-skills/blob/main/skills/sourcecoop/SKILL.md).

## Getting Started

To start, we'll install the Portolan skills plugin in our Claude Code instance. In this session, we're using Claude Opus 5.5. The total runtime for the session was about 90 minutes, and used 52 million tokens, which at current API prices comes to about $24, although in reality this is much cheaper on a subscription. I ran the session on a 20x Max plan and had no issues, but if you're on a Pro plan, you'd likely hit the usage limit at least once, or consider switching to a cheaper model like Sonnet (we haven't done evals to compare these, but anecdotally, we think Sonnet handles tasks like this fairly well).

We're using Claude Code CLI here, and running on a laptop with 16 cores and 64 GB of RAM. While these skills work fine in Claude Cowork, too, Cowork's stricter sandboxing and smaller virtual machines can lead to difficulties in accessing and processing the data, so we generally prefer to use the CLI. This would also work fine with Codex, Gemini, and other LLMs, and we include documentation and a quickstart guide in the Portolan skills repository.

## Planning up front

The first thing that Claude will do, per the `bootstrap`instructions, is explore the data source and plan its work. (You may want to explicitly switch into Claude's `plan` mode for this step.) It will do some research to understand what it's working with, identify any potential stumbling blocks, and also ask for my input on key decisions. For example, in this session, Claude ran into some issues with the licensing of a few of the upstream datasets, which it asked me about:

Before writing a plan, Claude stops to ask me four questions. The service states no license. All it has is an "as is" disclaimer, and the tax parcel lines are marked as copyright Suffolk County, used with permission. Claude can't settle that on its own, so it asks, and it recommends labeling the license "other" and leaving the parcels out. It also asks which of the 53 layers to mirror, because some are duplicates and the service says some of its data is draft.

After some iteration and getting my input, Claude will propose a plan for my approval.

## Creating and publishing the catalog

Under the hood, Claude is instructed to use `portolan-cli`, which is a CLI that ships a bunch of convenience tooling we've developed for creating Portolan catalogs. The CLI handles things like extracting data from upstream Esri or WFS servers, converting it to cloud-optimized file formats, organizing it as a STAC catalog, and enriching it with metadata extracted from the original source.

> Key note: the CLI is deterministic, meaning that it's all scripts. This is more reliable than prompting an agent, and costs far fewer tokens.

The CLI also allows Claude to dry run the extraction before starting. In this case, the dry run reveals some issues with how the data would be extracted, which Claude troubleshoots and fixes before proceeding, as well as filing [a bug report in the Portolan CLI repository](https://github.com/portolan-sdi/portolan-cli/issues/1003).

## Publication

Once the catalog is cleaned up, Claude is ready to publish it. For our purposes, there are two steps here that we care about: publishing the data to Source Cooperative and adding the published catalog to the Portolan registry. (In a future post, we'll talk about publishing the catalog metadata to GitHub with continuous integration.)

Claude ues the Source Coop skill and the CLI, following the Source Coop docs.

<PostFigure
  n={7}
  src="/img/tutorials/east-hampton-source-coop.webp"
  alt="Claude reports that the East Hampton catalog is published on Source Cooperative: 38 collections in 6 subcatalogs, 76 data files (57 MB), and 214 metadata files."
  ratio="1600 / 1296"
  caption="The catalog is live on Source Cooperative."
/>

One the data are published, Claude will add them to the Portolan registry. The registry is a kind of catalog of catalogs: a federated network of all public Portolan catalogs. This means that catalog owners can keep their data in their own storage while making it easily findable, searchable, and accessilble for users, like via the Portolan registry QGIS plugin or the reading Portolan skill.
